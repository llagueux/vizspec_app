Feature delivery reference

Git commands for a safe feature workflow

A visual companion to the Planner - Dev - Reviewer process. Follow the flow from a current main branch to a reviewed pull request, then return to an updated main.

The delivery flow

Complete one roadmap feature at a time. A dependent feature starts only after its prerequisite is merged and local main is current.

One-time setup

Configure repository hooks
# Use this repository's hook scripts, including the protected-branch guard.
$ git config core.hooksPath .githooks

Tells Git to look for this repository's hook scripts in .githooks/ instead of Git's default .git/hooks/ directory.

When you run git commit, Git executes the pre-commit hook from that folder. Here, that hook prevents commits on protected branches such as main.

The setting is stored locally in this clone, so each developer must run it once after cloning. Confirm it with git config --get core.hooksPath; it should print .githooks.

Verify the guard hook
# Confirm that the Copilot guard hook is configured correctly.
$ node .github/hooks/guard.test.cjs

Verifies that the Copilot guard hook is configured correctly.

1. Prepare the starting point

Check your worktree, update remote references, then bring local main forward without a merge commit.

Terminal
# 1. See the active branch, its remote tracking status, and changed files.
$ git status --short --branch

# 2. Download the latest remote branch references without modifying files.
$ git fetch origin

# 3. Return to the integration branch before creating the feature branch.
$ git switch main

# 4. Fast-forward local main to origin/main; stop if a merge would be needed.
$ git pull --ff-only origin main

# 5. Confirm that main, not a feature branch, is currently checked out.
$ git branch --show-current
Why this order matters: check for work that could be affected before switching branches, refresh your view of the remote, then create the feature branch from the latest main. Begin with no uncommitted changes, except for the roadmap file when the workflow permits it.

2. Create the feature branch

Replace <branch> with the branch declared for the selected roadmap feature, for example feat/budget-dashboard.

Main: current base for a new branch Feature: active branch ready for implementation
Create or resume a branch
# Create a new branch from the current main branch and switch to it.
$ git switch -c <branch>

# Or, resume an existing feature branch without creating another one.
$ git switch <branch>

# Confirm that your edits will happen on the roadmap branch, not main.
$ git branch --show-current
Branch names: use feat/, fix/, refactor/, or chore/, followed by a kebab-case slug of at most 40 characters.

3. Implement and inspect the feature

The feature branch advances while main remains stable. Each completed roadmap step becomes a focused Conventional Commit.

Main: stable integration Feature: commits and inspection
CommandWhy use it
git status --shortCheck precisely which files will be in the next commit.
git diffReview unstaged changes before staging.
git diff --stagedReview exactly what will be committed.
git add <path>...Stage only files belonging to the completed roadmap step. Avoid git add . unless every change is intentional.
git commit -m "type(scope): summary"Create one Conventional Commit for the roadmap step.
git log main..HEAD --onelineList commits delivered by the current feature branch.
git diff main...HEADInspect the complete feature diff before review.
Common types: feat, fix, refactor, chore, test, and docs.

4. Publish and merge the reviewed feature

Only continue after the feature has passed its checks and Reviewer review.

Feature: publish and request review Green: approved pull-request merge Main: synchronized for the next feature
Publish, review, merge, and synchronize
# First push: publish the branch and remember its upstream on origin.
$ git push -u origin <branch>

# Later pushes: send new commits to that remembered upstream branch.
$ git push

# Create a PR into main and prefill its title and description from commits.
$ gh pr create --base main --head <branch> --fill

# Open the current branch's PR in a browser to inspect it before merging.
$ gh pr view --web

# Merge the approved PR with a merge commit and remove the remote branch.
$ gh pr merge --merge --delete-branch

# Return to main and download the merged work before the next feature.
$ git switch main && git pull --ff-only origin main
Before submitting: review the title and body that gh pr create --fill generates from the commit history.

Commands intentionally not run by agents

Agents do not run git push, git merge, git rebase, git reset, git checkout, branch-deletion commands, or database migrations. These operations can rewrite history, remove work, or change the integration branch. Use the reviewed pull-request workflow instead.

Do not commit application code directly on main, master, develop, or production.
